# 目标架构

## Cortex-M 设备

虽然 RTIC 目前可以面向所有 Cortex-M 设备, 但用户应当了解一些关键的架构差异. 具体而言, ARMv6-M 与 ARMv8-M-base 架构中缺少基优先级屏蔽寄存器 (`BASEPRI`), 而该寄存器恰恰非常适合 RTIC 所使用的硬件优先级上限机制, 因此在这两种架构上 RTIC 不得不改用源屏蔽 ( source masking ). 关于 `lock` 的每一种实现及其详尽的优缺点评注, 请参阅 [`src/export.rs` 中 `lock` 的实现][src_export].

[src_export]: https://github.com/rtic-rs/rtic/blob/master/rtic/src/export.rs

这些差异会影响临界区的实现方式, 但功能应当保持一致, 唯一的例外是 ARMv6-M/ARMv8-M-base 无法让绑定到异常处理函数的共享资源任务存在, 因为这些资源无法在硬件上被屏蔽.

下面的表 1 列出了 Cortex-M 处理器及其所采用的临界区实现类型.

#### *表 1: 各处理器架构下的临界区实现*

| 处理器      |     架构     | 优先级上限 | 源屏蔽 |
| :---------- | :----------: | :--------: | :----: |
| Cortex-M0   | ARMv6-M      |            |   ✓    |
| Cortex-M0+  | ARMv6-M      |            |   ✓    |
| Cortex-M3   | ARMv7-M      |     ✓      |        |
| Cortex-M4   | ARMv7-M      |     ✓      |        |
| Cortex-M7   | ARMv7-M      |     ✓      |        |
| Cortex-M23  | ARMv8-M-base |            |   ✓    |
| Cortex-M33  | ARMv8-M-main |     ✓      |        |

### 源屏蔽

在没有 `BASEPRI` 寄存器 ( 它允许在嵌套向量中断控制器 NVIC 中直接设置优先级上限 ) 的情况下, RTIC 必须转而依靠禁用 ( 屏蔽 ) 中断来实现. 考虑下面的图 1, 其中任务 A 与 B 共享一个资源, 且 A 的优先级高于 B.

#### *图 1: 共享资源与源屏蔽*

```text
  ┌────────────────────────────────────────────────────────────────┐
  │                                                                │
  │                                                                │
3 │                   Pending    Preempts                          │
2 │             ↑- - -A- - - - -↓A─────────►                       │
1 │          B───────────────────► - - - - B────────►              │
0 │Idle┌─────►                             Resumes  ┌────────►     │
  ├────┴────────────────────────────────────────────┴──────────────┤
  │                                                                │
  └────────────────────────────────────────────────────────────────┴──► Time
                t1    t2        t3         t4
```

在时刻 *t1*, 任务 B 通过 NVIC 选择性地禁用所有其他与 B 共享资源的任务 ( 其优先级等于或低于这些任务 ), 从而锁定共享资源. 实际上, 这就在 NVIC 上形成了一个虚拟的优先级上限, 其效果与 `BASEPRI` 方案相同. 任务 A 就是与任务 B 共享资源的任务之一. 在时刻 *t2*, 任务 A 要么被任务 B 派生, 要么因中断条件而进入挂起, 但尽管其优先级更高, 此刻却尚未抢占任务 B. 这是因为 NVIC 正在阻止任务 A 启动, 原因正是任务 A 已被禁用. 在时刻 *t3*, 任务 B 通过在 NVIC 中重新启用这些任务来释放锁. 由于任务 A 此前已处于挂起状态, 且其优先级高于任务 B, 因此任务 A 立即抢占任务 B, 并可以在不存在数据竞争风险的前提下使用该共享资源. 在时刻 *t4*, 任务 A 完成执行, 将执行上下文交还给 B.

由于源屏蔽依赖于 NVIC, 因此像 HardFault、SVCall、PendSV 与 SysTick 等核心异常源不能与其他任务共享数据.

## RISC-V 设备

当前所有 RISC-V 后端的工作方式都与使用优先级上限的 Cortex-M 设备类似. 因此, 本书的 [资源](../by-example/resources.html) 页面是一个不错的参考. 不过, 其中一些后端并非完整的硬件实现, 而是用软件来模拟物理中断控制器. 因此, 这些后端并不实现硬件任务, 只需要软件任务. 而且对于这些目标, 软件任务的数量不受可用物理中断源数量的限制.

下面的表 2 比较了可用的 RISC-V 后端.

#### *表 2: 各处理器架构下的临界区实现*

| 后端                      |    兼容目标    | 后端专属配置 | 硬件任务 | 软件任务 | 任务数受硬件限制 |
| :-----------------------: | :------------: | :----------: | :------: | :------: | :--------------: |
| `riscv-esp32c3-backend`   |  仅 ESP32-C3   |              |    ✓     |    ✓     |        ✓         |
| `riscv-mecall-backend`    | 任何 RISC-V 设备 |              |          |    ✓     |                  |
| `riscv-clint-backend`     | 具有 CLINT 外设的设备 |      ✓       |          |    ✓     |                  |

### `riscv-mecall-backend`

无需在 `#[app]` 属性中提供 dispatchers 列表, RTIC 会在编译时生成它们. 优先级取值范围为 `0` ( 对应 `idle` 任务 ) 到 `255`.

### `riscv-clint-backend`

无需在 `#[app]` 属性中提供 `dispatchers` 列表, RTIC 会在编译时生成它们. 优先级取值范围为 `0` ( 对应 `idle` 任务 ) 到 `255`.

你**必须**在 `#[app]` 属性中包含一个 `backend` 专属配置, 以便 RTIC 知道用于标识运行你的应用的 HART 的 ID 编号. 例如, 对 `e310x` 芯片, 可按下面的方式配置一个最小应用:

```rust
#[rtic::app(device = e310x, backend = H0)]
mod app {
  // your application here
}
```

这样, RTIC 始终会引用 HART `H0`.
