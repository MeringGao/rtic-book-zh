# RTIC vs. 业界

RTIC 旨在为开发健壮可靠的嵌入式软件提供所需的最底层抽象.

它提供了一组最小的必需机制, 用于在中断和异步执行的任务之间安全地共享可变资源. 调度原语利用底层硬件来实现无与伦比的性能和可预测性, 实际上 RTIC 在 Rust 术语中为并发实时编程提供了零成本抽象.

## 关于安全性和安全性的比较

将 RTIC 与传统的实时操作系统 (RTOS) 进行比较是困难的. 首先, 传统的 RTOS 通常不提供任何关于系统安全性的保证, 即使是经过形式化验证的 [seL4] 内核这样的最强化内核也是如此. 它们对完整性、机密性和可用性的声明仅涉及内核本身 (在对其配置和环境的额外假设下). 它们甚至声明:

"经过验证或未经验证的 OS 内核, 都不会自动使系统安全. 事实上, 任何系统, 无论多么安全, 都可能以不安全的方式被使用." —— [seL4 FAQ][sel4faq]

[sel4faq]: https://docs.sel4.systems/projects/sel4/frequently-asked-questions.html

[seL4]: https://sel4.systems/

## 设计上的安全性

在信息安全领域, 我们通常会发现:

- 机密性, 保护信息不被未授权方获取,
- 完整性, 涉及数据的准确性和完整性, 以及
- 可用性, 涉及授权用户对数据的可访问性.

显然, 传统的 OS 既不能保证机密性, 也不能保证完整性, 因为两者都要求安全关键代码值得信任. 关于可用性, 这通常归结为系统资源的使用. 任何允许动态分配资源的 OS, 都依赖于应用程序正确处理分配/释放以及分配失败的情况.

因此它们的声明是正确的, 安全性完全超出了 OS 的掌控, 我们所能希望的最好结果是它不会增加进一步的漏洞.

而 RTIC 则为你保驾护航. 声明式的系统范围模型为你提供了一组静态的任务和资源, 并精确控制哪些数据被共享以及在哪些方之间共享. 此外, Rust 作为一种编程语言在完整性方面具有强大的特性 (编译时的别名、可变性和生命周期保证, 以及确保的数据有效性).

使用 RTIC, 这些特性会传递到系统范围的模型中, 而不会受到其他应用程序运行的干扰. RTIC 内核在内部是不可失败的, 不需要任何动态分配的数据.
